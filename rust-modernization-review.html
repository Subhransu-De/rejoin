Repository audit · 10 August 2026

Rust architecture & modern setup review

A practical review of rejoin against current Rust, Cargo, GitHub Actions, and mature Rust CLI practices. The goal is not to copy the complexity of a very large project; it is to identify the controls this repository can justify today.

Branch: main Baseline: aaeb2c3 Rust: 1.97.1 Edition: 2024 Scope: current working tree
Remediation update: this page records the original audit baseline. Implementation is now in progress on rust-modernization. Toolchain policy, terminal cleanup, scanner resilience, CLI integration tests, Cargo dependency policy, immutable action pins, bounded CI, GitHub-only installer publication, and contributor/security documentation have been implemented locally. Default-branch protection still requires an authorized live GitHub settings change, and trusted Windows signing still requires signing credentials.
Overall verdict

Modern core, incomplete hardening

The Rust codebase is fundamentally well set up. It uses Rust 2024, a committed lockfile, a clean binary-to-library entry point, sensible module boundaries, platform-gated Windows FFI, strict Clippy, cross-platform tests, CodeQL, dependency review, Dependabot, installer smoke tests, and release optimizations.

The repository is ready for continued development, but its release and governance layers are not yet as reproducible or enforceable as its code quality. The highest-value work is to protect main, define the supported/pinned Rust toolchain, harden action references, make tagged installers trustworthy and complete, and add scenario-level CLI tests.

Start here: what the findings mean

These four ideas explain most of the recommendations in the report.

CONCEPT 01

CI checks versus branch protection

CI runs tests and reports whether a change is healthy. Branch protection makes a passing result compulsory before GitHub accepts the change.

CI is the alarm; branch protection is the lock.

rejoin has a working alarm, but main currently has no lock. A direct push or manually merged failing change can bypass all of the good checks already present.

CONCEPT 02

Unit tests versus integration tests

A unit test proves one function works. An integration test launches the real executable with realistic files and checks stdout, stderr, JSON, and the exit code.

Unit tests inspect parts; integration tests take the finished car for a drive.

rejoin’s 17 tests cover useful parts, but they do not yet prove complete commands and failure paths from a user’s perspective.

CONCEPT 03

Edition, minimum Rust, and pinned Rust are different

edition = "2024" selects language rules. rust-version tells users the oldest supported compiler. rust-toolchain.toml tells contributors which compiler and components to install by default.

Edition is the grammar; MSRV is the oldest reader; the toolchain file is the exact printing press.

rejoin defines the grammar, but not the oldest supported reader or one consistent printing press.

CONCEPT 04

Validation versus distribution

Building and testing an installer proves that one artifact works. Publishing a separately built file does not transfer that proof to the file users download.

Testing one package and shipping another is like inspecting one product and boxing a different one.

The tagged release should publish the exact installer artifacts that passed smoke tests, signing, checksums, and provenance generation.

What is already correct

Strong

Rust language setup

  • edition = "2024", the current Rust edition.
  • No nightly-only language features.
  • cargo fmt and strict cargo clippy -D warnings pass.
  • Errors use anyhow::Result and contextual messages rather than pervasive panics.
  • The only production unsafe is narrowly scoped to Windows console FFI.
Sound

Architecture

  • main.rs is a three-line adapter into lib.rs.
  • Domain model, scanners, launching, handoff generation, app state, and rendering are separate modules.
  • Agent scanners are isolated behind one orchestration layer and use bounded file reads/cache support.
  • A workspace, async runtime, or dependency-injection framework would add complexity without a current need.
Strong baseline

Development & CI

  • CI runs format/Clippy and tests plus release builds on Linux, macOS, and Windows.
  • All Cargo CI commands use --locked.
  • Concurrency cancellation and least-privilege top-level permissions are present.
  • CodeQL, dependency review, Dependabot, secret scanning, and push protection are enabled.
  • Installer workflows smoke-test MSI install/uninstall and DEB/RPM packages.
Appropriate

Packaging foundations

  • Cargo.lock is tracked for the application.
  • Release profile uses thin LTO and strips symbols.
  • Linux and Windows archives carry SHA-256 checksums.
  • The audit-time cargo publish --dry-run --locked succeeded.
  • The modernization branch intentionally sets publish = false; GitHub Releases are the selected distribution channel.

Priority findings

1. CI exists, but main does not enforce it

High

The live repository has no branch protection and no repository ruleset. A direct push or merge can therefore bypass every passing check.

Lacking scenario
A regression reaches main despite failing CI, or history is force-pushed/deleted.
Evidence
GitHub API returned an empty ruleset list and “Branch not protected” for main.
Recommendation
Add a ruleset for the default branch: require pull requests, require the CI quality/test checks and CodeQL, block force pushes/deletion, require conversation resolution, and include administrators unless an explicit break-glass policy exists.
Done when
GitHub refuses a deliberately failing PR and a direct push, while a green PR can merge normally.

2. Tagged releases do not publish the validated native installers

High

installers.yml builds and smoke-tests MSI, DEB, and RPM artifacts, but only for pull requests or manual dispatch. release.yml independently publishes an x64 Linux tarball and Windows ZIP. It neither consumes the validated installers nor signs Windows artifacts. Provenance attestations run only for manually dispatched installer validation, not for the tagged release assets users download.

Lacking scenario
A release tag produces archives but no MSI/DEB/RPM, or a user cannot verify that the downloadable release was built by the tagged workflow. Windows SmartScreen reputation is also weakened by unsigned EXE/MSI files.
Evidence
.github/workflows/installers.yml and .github/workflows/release.yml are disconnected; current local edits remove Apple packaging but do not close this gap.
Recommendation
Make one tag-driven release graph build, smoke-test, checksum, attest, and upload MSI/DEB/RPM plus fallback archives. Sign both Windows EXE and MSI with a timestamped certificate before publication. Add crates.io and WinGet only after ownership/credential setup is confirmed.
Done when
A test tag yields only verified artifacts, gh attestation verify succeeds, MSI install/uninstall passes, and all intended assets appear in one GitHub Release.

3. Rust support and build toolchains are implicit and inconsistent

High

Cargo.toml has no rust-version, and the repository has no rust-toolchain.toml. Most CI/release jobs use the moving stable channel while Hawk alone uses exactly 1.97.1. A contributor, CI run, and release can therefore compile with different Rust versions on the same commit.

Lacking scenario
A dependency or compiler update breaks a release unexpectedly, or a source installer gets an obscure compiler error because the minimum supported Rust version was never declared.
Recommendation
Empirically determine MSRV, add rust-version, and check it in CI. Add a repository toolchain file with a deliberate policy: exact stable for reproducible local/release builds, plus a separate latest-stable CI lane if forward compatibility matters.
Suggested start
Use the already validated 1.97.1 as the development pin first; lower the MSRV only after an explicit test proves it.
Done when
cargo +<MSRV> check --locked passes, one documented command installs the expected components, and release logs show the intended exact compiler.

4. GitHub Actions use mutable tags

High

Actions such as actions/checkout@v7, actions/upload-artifact@v7, and actions/attest@v4 are convenient but mutable. GitHub identifies a full commit SHA as the only immutable action reference.

Lacking scenario
An upstream tag is moved or an action publisher is compromised, changing privileged release behavior without a repository diff.
Recommendation
Pin every uses: reference to a full commit SHA and retain the human-readable version in a comment. Dependabot already manages the github-actions ecosystem and can update SHA pins.
Related exposure
Hawk is installed through a downloaded shell script without a checked digest; pin/verify that installer too. Treat fedora:latest as an intentional compatibility test, not a reproducible release input.
Done when
A workflow scan finds no tag-only third-party action references and installer downloads are checksum-verified.

5. Terminal state restoration is not failure-safe

Medium

enter_terminal() enables raw mode before operations that can fail. If entering the alternate screen or creating the terminal fails, there is no guard to restore the prior state. Cleanup is manual and sequential, so one cleanup error can prevent the remaining cleanup and can replace the original error.

Lacking scenario
A terminal I/O error leaves the user’s shell in raw mode, on the alternate screen, or with a hidden cursor.
Evidence
src/lib.rs:139–202.
Recommendation
Introduce an RAII terminal-session guard that records completed setup steps and performs best-effort restoration in Drop. Preserve the primary operation error while attaching cleanup diagnostics.
Done when
Fault-injection tests fail each setup/cleanup step and always observe raw mode disabled, the primary screen restored, and the cursor shown.

6. Tests cover helpers, not complete CLI scenarios

Medium

The 17 tests are useful and fast, but there is no tests/ integration suite and no coverage measurement. The largest modules—app.rs, scanner/mod.rs, and ui.rs—are about 560–620 lines each, while several scanner backends have no direct tests.

Lacking scenarios
rejoin list --json output contract; all path overrides; empty/corrupt/truncated/non-UTF-8 stores; SQLite schema drift; scanner thread panic; terminal restoration; exit codes; agent executable missing; cache corruption; Unicode and narrow-terminal behavior.
Recommendation
Add black-box CLI tests using temporary homes and fixture stores. Keep Ratatui TestBackend tests. Add targeted malformed-input tests and a lightweight coverage report; set a threshold only after establishing a trustworthy baseline.
Architecture follow-up
Split large modules only along tested responsibilities—for example scanner orchestration/process detection and UI layout/widgets—not solely to reduce line counts.
Done when
Each user-visible subcommand and failure mode has at least one cross-platform contract test, and coverage trends are visible in CI.

7. Rust dependency policy is checked only indirectly

Medium

Dependabot, dependency review, CodeQL, and secret scanning form a good security baseline. However, cargo audit is not run in CI or on a schedule, and no policy verifies licenses, allowed registries/git sources, or duplicate-version exceptions. The local audit was clean, and all 259 registry packages reported license metadata, but that result is only a point-in-time observation.

Lacking scenario
A new RustSec advisory affects an unchanged lockfile between PRs, or a dependency enters from an unapproved source/license.
Recommendation
Add a scheduled and lockfile-triggered cargo deny check (or separate cargo audit plus license/source checks). Start with explicit allowlists and documented duplicate exceptions rather than blanket-denying every duplicate.
Done when
A known-vulnerable fixture and an unapproved source/license make the policy job fail with an actionable message.

8. Windows unsafe blocks have no safety justification

Medium

The Windows cursor query contains three small FFI unsafe blocks. Their scope is good, but the required invariants—valid standard handle, initialized output after API success, and pointer lifetime—are not documented or linted.

Lacking scenario
A future refactor changes an FFI invariant without making the reviewer reconsider safety.
Evidence
src/launch.rs:133–148.
Recommendation
Add precise // SAFETY: comments and enable clippy::undocumented_unsafe_blocks at the package level. Keep the lint targeted; enabling every pedantic/restriction lint is not inherently more modern.
Done when
Removing a safety comment causes Clippy CI to fail and the comments explain why each Windows call/initialization is valid.

9. The crates.io package is valid but not curated

Medium

The dry run succeeds, but package metadata omits rust-version, keywords, and categories. cargo package --list includes unrelated HTML, GitHub workflows, Hawk config, and native-installer sources. The current package is small, so this is hygiene rather than an immediate size problem.

Lacking scenario
A future visual/report asset or installer file silently bloats the published crate, and users cannot discover the CLI well on crates.io.
Recommendation
Use an explicit include allowlist for source-build requirements, add categories/keywords/MSRV, decide whether the library API is intentionally public, and add cargo publish --dry-run --locked to release validation.
Current evidence
Before this report was added: 34 packaged files, 266.6 KiB unpacked / 64.8 KiB compressed.
Done when
The package list contains only files needed to build, license, document, and use the crate; the packaged crate verifies from scratch.

10. Contributor and security workflows are tribal knowledge

Normal

The README documents build and test commands, but there is no CONTRIBUTING.md or SECURITY.md, and it does not describe the exact toolchain, formatting, Clippy, Hawk, audit, actionlint, packaging, or release procedure.

Lacking scenario
A new contributor gets locally green code that fails CI, or a vulnerability is disclosed publicly because no private reporting path is documented.
Recommendation
Add concise contributor and security guides. A task runner is optional; one canonical documented command sequence is enough for a repository this size.
Done when
A clean-machine contributor can reproduce CI from the docs and the Security tab/reporting policy points to a private disclosure route.

11. CI can be more bounded and efficient

Normal

Quality, test, CodeQL, and dependency-review jobs have no job timeout; only Hawk and packaging jobs are bounded. The test matrix recompiles dependencies on every OS without an explicit cache. Release coverage is host x64 Linux/Windows only.

Lacking scenarios
A hung tool consumes runner time indefinitely; routine PRs spend most time rebuilding; ARM64 or static-Linux users have no first-party archive.
Recommendation
Add sensible job timeouts, then add a SHA-pinned Rust cache if measurements justify it. Consider x86_64 musl and ARM64 only when distribution demand exists; do not confuse a larger target matrix with better architecture.
Done when
Jobs terminate within documented bounds, cache hit rates are observable, and each advertised platform is smoke-tested.

One important Rust design improvement: a terminal guard

A TUI temporarily changes global terminal state. The current implementation restores that state manually, but an error can occur between setup steps. Rust’s ownership model provides a stronger pattern: create an object that owns the terminal session and restores it automatically when the object goes out of scope.

Create guard
→
Record raw mode enabled
→
Record alternate screen entered
→
Run application
→
Drop restores every completed step
Why this is better: cleanup runs on a normal return, an early ? error, and panic unwinding. Each cleanup operation should be attempted even if another cleanup operation fails, and the original application error should remain the primary error.

Modernization does not mean adding unnecessary complexity

The following commonly suggested changes are not justified for rejoin today.

No workspace yet

There is one meaningful crate. A Cargo workspace becomes useful when multiple independently built crates have a real ownership or reuse boundary.

No async runtime needed

The application mostly performs filesystem scanning, SQLite access, process inspection, and terminal interaction. Adding Tokio would increase complexity without a demonstrated benefit.

No framework migration

The current module architecture is understandable. Dependency injection or microcrates would add indirection; tested responsibility boundaries are more valuable.

No lint maximalism

Strict default Clippy already passes. Add targeted lints such as undocumented unsafe blocks instead of enabling every opinionated restriction lint.

No arbitrary coverage target

First add meaningful CLI scenarios and observe the baseline. A percentage is useful only when it reflects important behavior, not test inflation.

No target-matrix race

ARM64 and static musl releases are useful when users need them. More targets are a distribution choice, not proof of better Rust architecture.

The right goal for rejoin: keep the application architecture simple while making builds, tests, releases, dependency policy, and failure recovery dependable.

Recommended sequence

  1. Enforce the baselineCreate a default-branch ruleset requiring the already-green CI, CodeQL, and review policy.
  2. Make Rust support explicitAdd MSRV/toolchain policy, align local/CI/release compilers, and test both supported-minimum and current stable.
  3. Close the release chainUnify tagged archives and validated installers; sign, checksum, attest, smoke-test, then publish.
  4. Harden the automation supply chainPin actions and downloaded tooling immutably; add scheduled RustSec/license/source policy checks.
  5. Make runtime failures safeAdd the terminal guard, document Windows unsafe invariants, and remove panic-only scanner join handling where recovery is possible.
  6. Add behavior-level confidenceBuild fixture-driven CLI integration tests for output contracts, corrupt stores, path overrides, and platform failure modes.
  7. Finish project ergonomicsCurate the crate payload/metadata and add short contributor and security guides; optimize CI only after measuring it.
